Overview

Control Plane is a multi-agent orchestration system for data analysis and workflows. It uses GPT-5.1 (Boss) and Claude Sonnet (Worker) to classify tasks, split them into steps, and run them with verification and retries. The pipeline is manifest-driven: you describe the task in a JSON manifest and run without code changes. Outputs are written under a timestamped run directory with phase-specific artifacts, a file catalog, and an end-to-end summary.

Entryrun_control_plane.py --manifest <path>
Phases0 (Classify) → 1 (Divide) → 2 (Execute)
ModelsGPT-5.1 (Boss), Claude Sonnet (Worker)
Outputruns/run_YYYYMMDD_HHMMSS/

High-level flow: Manifest → Phase 0 (task classification) → Phase 1 (task division / execution plan) → Phase 2 (Boss–Worker execution) → Outputs.

Phase Role(s) Model(s) Purpose
0 Classifier, Overseer Claude Sonnet, GPT-5.1 Initial task analysis; identify core vs side tasks; optional side-task execution (skippable via manifest).
1 Divider Claude + GPT-5.1 Structure analysis (code execution), then collaborative debate to produce execution plan (execution_plan.json).
2 Boss, Worker GPT-5.1 (Boss), Claude Sonnet (Worker) Boss delegates subtasks to Worker; Worker runs code, file edits, PDF extraction, RAG, TODOs; Boss verifies and can redelegate.

Phase 2 Boss–Worker Sequence

For each task in the execution plan, the orchestrator runs this loop:

sequenceDiagram participant Orch as Orchestrator participant Boss as Boss (GPT-5.1) participant Worker as Worker (Claude) Orch->>Boss: TaskMessage with work_scope Boss->>Worker: Delegate subtask Worker->>Worker: Run tools: code, file edit, PDF, RAG Worker->>Boss: TaskCompletionMessage + outputs Boss->>Boss: Verify results alt Accept Boss->>Orch: Task complete; update catalog else Redelegate Boss->>Worker: Refined instructions Worker->>Boss: Updated results end Orch->>Orch: Next task or finish

Data Flow

flowchart LR A[1. Manifest load] --> B[2. user_uploads copy] B --> C[3. Phase 0 classify] C --> D[4. Phase 1 plan] D --> E[5. Phase 2 execute] E --> F[6. outputs]
  1. Manifest load – Path from CLI --manifest; JSON loaded; paths resolved (e.g. user_uploads).
  2. User uploads – Files listed in manifest["user_uploads"] are copied to runs/<run_id>/user_uploads/.
  3. Phase 0 – Cleaned manifest + context → TaskClassifier → TaskClassification (core_tasks, side_tasks). Optional: SideTaskSolver runs; output under phase0/.
  4. Phase 1 – Core task + manifest → CollaborativeTaskDivider → phase1/structure_analysis.json, then phase1/execution_plan.json.
  5. Phase 2 – Orchestrator reads execution_plan.json; for each task, Boss delegates to Worker; Worker uses tools, writes to task outputs/ and tool_results/; Boss verifies; results and file catalog updated.
  6. Outputs – Run directory contains file_catalog.json, vector_store.pkl, e2e_summary.json; phase dirs contain phase-specific artifacts and logs.

Manifest and Config

Manifest

The manifest is a JSON file that defines the task, inputs, and options. Key fields include: task_id, task_type, description, user_uploads (array of source and filename), skip_side_tasks, transformation_config, required_deliverables, worker_instructions, and optional execution_preferences. Paths are resolved relative to the project root; user_uploads entries are copied into the run’s user_uploads folder. Example: manifests/manifest_amazon_analysis.json.

Environment

env_info.json at the project root (not committed; see env_info.json.example) holds:

  • llm_config.azure – Azure OpenAI endpoint, api_key, deployment names (e.g. gpt5_model, gpt41_deployment); optional chat_endpoint / chat_api_key for a separate chat resource.
  • llm_config.anthropic_azure – Azure Anthropic (Claude): endpoint, api_key, sonnet_deployment. Used when use_azure_for_claude is true.
  • llm_config.bedrock – Optional; AWS Bedrock for Claude if not using Azure Anthropic.
  • database_config, external_apis – For DB and external services (e.g. Tavily) when needed.
